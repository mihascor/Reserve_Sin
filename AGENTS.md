# AGENTS.md

## Роль в проекте

Вы работаете в качестве помощника программиста в этом репозитории.
Не придумывайте требования к продукту. Сначала следуйте документации в /docs.

Перед внесением изменений:
- прочтите соответствующую документацию в /docs;
- проверьте существующие файлы;
- кратко объясните, что вы собираетесь изменить;
- внесите минимальное безопасное изменение.

## Документирование

Поддерживай документацию проекта одновременно с изменениями кода. Обновляй только документы, на которые реально влияет выполненная задача. Описывай фактическое состояние проекта и отдельно отмечай запланированные, но ещё не реализованные возможности. Не придумывай команды, компоненты, настройки и архитектурные решения. Не дублируй одинаковую информацию в разных документах и не добавляй секреты или реальные значения переменных окружения. При расхождении кода, технического задания и документации укажи это в отчёте, не меняя требования самостоятельно.

## Стиль разработки

Работайте поэтапно.

Не переписывайте большие части проекта, если это явно не требуется.

Предпочитайте небольшие коммиты/небольшие изменения.
Сохраняйте существующую архитектуру и соглашения об именовании.

После каждой задачи сообщайте:
- какие файлы были изменены;
- почему они были изменены;
- как проверить результат;
- что еще предстоит сделать.

## Правила безопасности

Не добавляйте в репозиторий секреты, токены, пароли, ключи API, cookie или закрытые учетные данные.
Не прописывайте учетные данные для производственной среды.
Используйте переменные окружения для конфигурации.
Если существует `.env.example`, обновляйте его при необходимости добавления новых переменных.

## Правила архитектуры

Уважайте выбранную архитектуру.

Не добавляйте новые фреймворки или тяжелые зависимости без одобрения.

Если новая зависимость кажется необходимой, объясните:
- почему она необходима;
- какие существуют альтернативы;
- какой риск она добавляет.

## Качество кода

Делайте код простым и читаемым.
Предпочитайте явные имена сложным абстракциям.
Добавляйте комментарии только там, где они разъясняют неочевидную логику.
Не усложняйте функции раннего MVP.

## Тестирование

При изменении логики добавляй или обновляй автоматические тесты для затронутого поведения. Перед завершением задачи запускай доступные проверки проекта и сообщай, какие тесты выполнены, какие не запускались и по какой причине. Не утверждай, что изменение работает, если это не подтверждено тестами или ручной проверкой.

## Валидация

Проверяй входные данные на сервере независимо от клиентской проверки. Используй существующие правила и инструменты проекта, не дублируй схемы без необходимости. Для некорректных данных возвращай понятные ошибки без раскрытия внутренних деталей системы и добавляй проверки граничных случаев.

## Ведение версий

Используй семантическое версирование `MAJOR.MINOR.PATCH`. Храни текущую версию в одном основном конфигурационном файле проекта и не дублируй её вручную без необходимости. Все заметные изменения добавляй в `CHANGELOG.md` по категориям: 
- добавлено, 
- изменено, 
- исправлено
- удалено. 
Не изменяй номер версии и не создавай Git-теги без прямого указания пользователя.

## Логирование

При изменении проекта используй установленную систему логирования и соблюдай её текущую архитектуру, конфигурацию и принятый формат записей. Не добавляй другую библиотеку логирования и не заменяй существующую систему без отдельного требования пользователя.

Новые функции и модули должны использовать общий механизм логирования проекта, поддерживать принятые уровни логов и передавать идентификатор запроса или другой контекст, если это предусмотрено архитектурой.

Сохраняй разделение настроек для разработки и продакшена. Не записывай в логи пароли, токены, API-ключи, персональные данные, платёжную информацию и другое конфиденциальное содержимое.

При изменении конфигурации логирования сначала проверь существующие настройки, переменные окружения и документацию. Не нарушай работу приложения при недоступности внешнего хранилища логов.




## Адаптивность и визуальная проверка

## Адаптивность и визуальная проверка
Все изменения интерфейса должны проверяться не только на текущем размере окна.

Обязательные контрольные ширины:

- mobile: 320, 375, 390 px;
- tablet: 768, 1024 px;
- desktop: 1280, 1366, 1440, 1920 px.

Для desktop дополнительно проверять масштаб браузера:

- 100%;
- 125%;
- 150%;
- 200%.

Требования:

- элементы не должны перекрывать друг друга;
- текст и значения не должны выходить за границы карточек;
- длинные заголовки должны переноситься или безопасно сокращаться;
- пользовательская страница не должна получать горизонтальный скролл из-за отдельной карточки;
- широкие таблицы должны иметь локальный горизонтальный скролл;
- grid/flex-компоновка должна перестраиваться при нехватке ширины;
- для сжимаемых grid/flex-элементов проверять необходимость `min-width: 0`;
- не использовать `overflow: hidden` только для сокрытия ошибки компоновки;
- не использовать `transform: scale()` как основной механизм адаптивности;
- не уменьшать шрифт до нечитаемого размера ради сохранения количества колонок.

Обычные страницы должны быть адаптивными.

Capture-страницы:

- проверяются отдельно;
- используют согласованный фиксированный desktop viewport;
- снимаются при масштабе браузера 100%;
- не обязаны поддерживать мобильную компоновку;
- не должны зависеть от случайного размера окна браузера.

После значительных изменений фронтенда:

1. проверить существующий dev-сервер на `http://127.0.0.1:3000`;
2. открыть изменённые маршруты в браузере;
3. проверить контрольные размеры viewport;
4. проверить отсутствие переполнения и наложения;
5. запустить линтер и production build;
6. сообщить, какие разрешения и маршруты были фактически проверены.

Нельзя считать задачу по адаптивности завершённой только на основании просмотра CSS или одного скриншота.

## Чистота репозитория

Не добавляйте в Git генерируемые, временные и локальные файлы:

- кэши и результаты сборки;
- логи;
- настройки IDE;
- файлы операционной системы;
- локальные данные и загрузки;
- служебные файлы тестовых инструментов;
- файлы окружения с секретами.

Перед завершением задачи:

1. Выполните `git status --short`.
2. Проверьте каждый новый файл.
3. Если файл генерируется автоматически и не является исходным кодом, миграцией, документацией, тестом или необходимой конфигурацией — добавьте его в `.gitignore`.
4. Не добавляйте файл в Git только потому, что он используется локально.
5. Не удаляйте уже отслеживаемые файлы без проверки их назначения.
6. Не считайте принцип «не участвует в production» единственным критерием: тесты, документация, миграции, скрипты разработки и примеры конфигурации должны храниться в репозитории.
