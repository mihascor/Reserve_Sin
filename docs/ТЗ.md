ТЕХНИЧЕСКОЕ ЗАДАНИЕ
Проект: Reserve_Sin

1. НАЗНАЧЕНИЕ ПРОЕКТА

Разработать персональное Android-приложение для ручного учёта накоплений по отдельным категориям.

Приложение предназначено для одного пользователя.

Приложение:

- не подключается к банкам;
- не получает банковские выписки;
- не хранит банковские реквизиты;
- не выполняет реальные денежные переводы;
- хранит только введённые пользователем сведения о накоплениях;
- позволяет вручную добавлять поступления и списания;
- показывает остаток по каждой категории;
- показывает общую сумму накоплений;
- хранит полную историю изменений;
- синхронизирует данные между Android-приложением и личным сервером.

Существующая таблица используется как основа логики. Формат интерфейса необходимо адаптировать для экрана телефона.

2. ИСХОДНАЯ СТРУКТУРА УЧЁТА

В существующей таблице используются:

- дата операции;
- дополнительная метка или тип операции;
- отдельные категории накоплений;
- положительные суммы — поступления;
- отрицательные суммы — списания;
- текущий остаток по каждой категории;
- общий остаток по всем категориям.

Начальные категории:

1. Подушка
2. Катя
3. На отдых
4. Кладбище
5. На налоги

Категории «Пусто 1», «Пусто 2», «Пусто 3» создавать не нужно.

Новые категории пользователь должен добавлять самостоятельно через настройки приложения.

На момент предоставленного снимка таблицы отображаются следующие остатки:

- Подушка — 92 600 руб.
- Катя — 16 000 руб.
- На отдых — 121 600 руб.
- Кладбище — 5 000 руб.
- На налоги — 11 400 руб.
- Общая сумма — 246 600 руб.

Эти значения не должны быть жёстко записаны в программном коде. При переносе данных они должны быть сформированы историей операций или отдельными начальными операциями.

3. ОСНОВНЫЕ ПРИНЦИПЫ УЧЁТА

3.1. Денежные суммы

Все суммы хранятся как целые числа в рублях.

Пример:

- 1 000 рублей хранится как 1000;
- отрицательное значение используется для списания.

Использование float и double для денежных сумм запрещено.

В первой версии используется только валюта RUB.

3.2. Операции

Каждое изменение остатка оформляется как отдельная операция.

Операция содержит:

- уникальный идентификатор;
- категорию накоплений;
- сумму;
- дату операции;
- необязательную метку или тип;
- необязательный комментарий;
- дату создания;
- дату последнего изменения;
- идентификатор клиентской операции;
- статус отмены;
- статус синхронизации на Android.

Положительная сумма увеличивает остаток категории.

Отрицательная сумма уменьшает остаток категории.

Остаток категории рассчитывается как сумма всех неотменённых операций данной категории.

Общий остаток рассчитывается как сумма остатков всех активных категорий.

Хранить итоговые остатки как единственный источник данных запрещено. Источником данных является история операций.

3.3. Групповые операции

Существующая таблица позволяет указывать несколько изменений по разным категориям в одной строке и на одну дату.

В приложении необходимо сохранить эту возможность.

Пользователь должен иметь возможность создать групповую операцию, содержащую:

- общую дату;
- общую метку или тип;
- общий комментарий;
- одну или несколько строк с категорией и суммой.

Пример групповой операции:

Дата: 31.07.2026

- Подушка: +57 025 руб.
- На отдых: +111 600 руб.
- На налоги: +11 400 руб.

Каждая строка групповой операции хранится как отдельная транзакция, но все строки имеют общий batch_id или operation_group_id.

Также групповой операцией можно оформить перенос между категориями:

- Подушка: -5 000 руб.
- На отдых: +5 000 руб.

Приложение не должно требовать, чтобы сумма групповой операции была равна нулю.

3.4. Исправление операций

Операции желательно не удалять физически.

Для удаления должна использоваться мягкая отмена:

- операция получает статус is_cancelled;
- отменённая операция не участвует в расчёте остатков;
- запись остаётся в истории.

Для исправления уже синхронизированной суммы рекомендуется:

- отменить ошибочную операцию;
- создать новую корректную операцию.

Операцию, которая ещё не отправлена на сервер, разрешается редактировать локально.

4. КАТЕГОРИИ НАКОПЛЕНИЙ

Для каждой категории необходимо хранить:

- id;
- название;
- валюту;
- необязательную целевую сумму;
- порядок отображения;
- признак архивной категории;
- дату создания;
- дату изменения.

Через настройки пользователь должен иметь возможность:

- создать категорию;
- изменить название;
- указать целевую сумму;
- изменить порядок категорий;
- архивировать категорию;
- восстановить архивную категорию;
- выбрать, показывать ли категорию на главном экране.

Физическое удаление категории, по которой есть операции, запрещено.

Такая категория может быть только архивирована.

Архивная категория:

- не показывается среди активных категорий;
- остаётся доступной в истории;
- продолжает участвовать в старых операциях;
- может быть восстановлена.

Название категории не должно быть пустым.

Категории должны отображаться в заданном пользователем порядке.

5. МЕТКИ ОПЕРАЦИЙ

В существующей таблице присутствует дополнительный выпадающий список со значениями наподобие «Погашение» и «Долг».

В приложении это необходимо реализовать как необязательные метки операций.

Пользователь должен иметь возможность:

- создать метку;
- изменить название метки;
- выбрать метку при создании операции;
- архивировать метку;
- оставить операцию без метки.

Метка не влияет на денежный расчёт и используется только для классификации и фильтрации истории.

При переносе существующей таблицы необходимо уточнить полные названия используемых сейчас меток.

6. ЭКРАНЫ ANDROID-ПРИЛОЖЕНИЯ

6.1. Главный экран

Главный экран должен показывать:

- общую сумму накоплений;
- дату последней успешной синхронизации;
- состояние синхронизации;
- список активных категорий;
- текущий остаток каждой категории;
- целевую сумму категории, если она указана;
- прогресс накопления, если указана цель;
- кнопку добавления операции.

Категории должны отображаться вертикальным списком или карточками, адаптированными для телефона.

Для каждой категории показывать:

- название;
- текущий остаток;
- цель, если указана;
- процент достижения цели;
- индикатор наличия несинхронизированных изменений.

На главном экране не должно быть пустых заранее подготовленных колонок.

Новые категории появляются только после добавления через настройки.

6.2. Экран добавления операции

Форма должна содержать:

- дату операции;
- метку операции;
- комментарий;
- список строк операции;
- категорию в каждой строке;
- сумму в каждой строке;
- переключатель или выбор «Пополнение» / «Списание»;
- кнопку добавления дополнительной строки;
- кнопку сохранения.

По умолчанию устанавливается текущая дата.

Пользователь вводит сумму без знака и отдельно выбирает:

- пополнение;
- списание.

Внутри базы:

- пополнение сохраняется положительным числом;
- списание сохраняется отрицательным числом.

Дополнительно разрешить ввод суммы со знаком, если это не ухудшает удобство интерфейса.

Нельзя сохранить строку:

- без категории;
- без суммы;
- с нулевой суммой.

В одной групповой операции одна категория может использоваться несколько раз, однако приложение может предупреждать пользователя и предлагать объединить такие строки.

После сохранения операция сразу должна появиться в интерфейсе, даже если отсутствует интернет.

6.3. Экран истории

История должна отображаться в обратном хронологическом порядке.

Операции одной группы желательно визуально объединять.

Для каждой операции или группы показывать:

- дату;
- метку;
- комментарий;
- категории;
- суммы;
- общий результат группы;
- статус синхронизации;
- признак отмены.

Фильтры истории:

- период;
- категория;
- метка;
- пополнения;
- списания;
- отменённые операции;
- несинхронизированные операции.

Необходимо предусмотреть просмотр подробной информации об операции.

Из подробного просмотра пользователь должен иметь возможность:

- отменить операцию;
- повторить отправку при ошибке;
- создать исправленную копию;
- изменить локальную операцию, если она ещё не синхронизирована.

6.4. Экран категории

При открытии категории показывать:

- название;
- текущий остаток;
- цель;
- прогресс;
- историю операций только по этой категории;
- общую сумму пополнений за выбранный период;
- общую сумму списаний за выбранный период.

6.5. Экран настроек

Разделы настроек:

- управление категориями;
- управление метками;
- параметры синхронизации;
- адрес сервера;
- настройка токена;
- экспорт данных;
- информация о последней синхронизации;
- ручной запуск синхронизации;
- информация о приложении.

Адрес сервера по умолчанию:

https://reserve-sin.duckdns.org

API-токен не должен отображаться полностью после сохранения.

7. ЛОКАЛЬНАЯ РАБОТА И СИНХРОНИЗАЦИЯ

Приложение должно работать по принципу local-first.

Все данные, необходимые для работы интерфейса, хранятся локально в Room.

При добавлении операции:

1. Android создаёт уникальный client_operation_id.
2. Операция записывается в Room.
3. Операция получает статус PENDING.
4. Интерфейс сразу пересчитывает остатки.
5. Приложение пытается отправить операцию на сервер.
6. После подтверждения сервера статус меняется на SYNCED.
7. При ошибке статус меняется на ERROR.
8. WorkManager повторяет отправку позднее.

Статусы синхронизации:

- PENDING — ожидает отправки;
- SYNCED — успешно сохранено на сервере;
- ERROR — произошла ошибка;
- CANCEL_PENDING — ожидает отправки отмены.

Повторная отправка операции с тем же client_operation_id не должна создавать дубликат.

Сервер должен возвращать существующую операцию или успешный идемпотентный ответ.

При запуске приложения необходимо:

- показать локальные данные;
- запустить фоновую синхронизацию;
- получить изменения с сервера;
- обновить локальную базу;
- отправить накопившиеся локальные операции.

Для получения изменений использовать серверную ревизию.

Android хранит номер последней полученной revision.

Запрос:

GET /api/v1/changes?after={revision}

должен возвращать все изменения после указанной ревизии и новый номер текущей ревизии.

8. АВТОРИЗАЦИЯ

Пользователь один.

Не использовать:

- регистрацию;
- логин и пароль;
- OAuth;
- JWT;
- refresh-токены;
- ролевую модель.

Для доступа используется один постоянный Bearer API-токен.

Заголовок запроса:

Authorization: Bearer <token>

Токен:

- генерируется случайным образом;
- хранится на сервере в отдельном env-файле;
- вводится в Android-приложении при первоначальной настройке;
- защищается с помощью Android Keystore;
- не хранится открытым текстом в исходном коде;
- не записывается в логи;
- не передаётся по незащищённому HTTP.

При неверном токене сервер возвращает HTTP 401.

→ HTTPS

https://reserve-sin.duckdns.org

127.0.0.1:8080

Порт 8080 не открывается в интернет.

Снаружи открываются только необходимые порты:

- 80;
- 443;

AmneziaVPN работает независимо и не участвует в Reserve_Sin.

Docker для Reserve_Sin не используется.

13. REST API

Формат данных:

- JSON;
- кодировка UTF-8;
- даты и время в ISO 8601;
- денежные суммы в целых рублях;
- ошибки в едином JSON-формате.

Минимальные методы API.

13.1. Проверка сервера

GET /health

Ответ должен показывать:

- состояние приложения;
- доступность базы данных;
- версию серверного приложения.

Метод /health не должен раскрывать токен, пути к файлам и другие чувствительные данные.

13.2. Категории

GET /api/v1/categories

Получить категории.

POST /api/v1/categories

Создать категорию.

PATCH /api/v1/categories/{id}

Изменить название, цель, порядок или статус архива.

13.3. Метки

GET /api/v1/labels

Получить метки.

POST /api/v1/labels

Создать метку.

PATCH /api/v1/labels/{id}

Изменить или архивировать метку.

13.4. Операции

GET /api/v1/transactions

Поддерживаемые параметры:

- after;
- before;
- category_id;
- label_id;
- include_cancelled;
- limit;
- cursor.

POST /api/v1/transactions

Создать одиночную операцию.

POST /api/v1/transaction-batches

Создать групповую операцию.

PATCH /api/v1/transactions/{id}

Разрешённые изменения определяются правилами аудита.

POST /api/v1/transactions/{id}/cancel

Отменить операцию без физического удаления.

13.5. Сводка

GET /api/v1/summary

Ответ должен содержать:

- общий остаток;
- остатки по категориям;
- цели;
- прогресс по целям;
- дату последней операции;
- текущую серверную revision.

13.6. Синхронизация

GET /api/v1/changes?after={revision}

Возвращает:

- изменённые категории;
- изменённые метки;
- созданные и изменённые операции;
- отменённые операции;
- текущую revision.

14. ФОРМАТ ОШИБОК API

Ошибки возвращаются в формате:

{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некорректная сумма",
    "details": {}
  }
}

Основные HTTP-коды:

- 200 — успешное получение или изменение;
- 201 — объект создан;
- 400 — неверные данные;
- 401 — неверный токен;
- 404 — объект не найден;
- 409 — конфликт или повтор идентификатора;
- 500 — внутренняя ошибка сервера.

Технические подробности внутренних ошибок не должны передаваться Android-приложению.

15. РАЗМЕЩЕНИЕ НА СЕРВЕРЕ

Исполняемый файл:

/opt/reserve-sin/reserve-server

База данных:

/var/lib/reserve-sin/reserve.db

Настройки и токен:

/etc/reserve-sin/reserve.env

Резервные копии:

/var/backups/reserve-sin/

Владелец файлов:

reserve-sin

Права доступа должны запрещать чтение env-файла и базы посторонними системными пользователями.

16. РЕЗЕРВНОЕ КОПИРОВАНИЕ

Необходимо настроить ежедневную резервную копию SQLite.

Для резервного копирования использовать:

- SQLite backup API;
или
- VACUUM INTO.

Запрещено копировать активную SQLite-базу в режиме WAL обычной командой cp.

Требования:

- одна автоматическая копия в день;
- хранение нескольких последних ежедневных копий;
- удаление старых копий по настроенному сроку;
- журналирование результата резервного копирования;
- возможность ручного запуска;
- документированная процедура восстановления.

Рекомендуемый срок хранения — последние 14 ежедневных копий.

17. ЭКСПОРТ ДАННЫХ

В Android-приложении предусмотреть экспорт в CSV.

Экспорт должен включать:

- дату;
- категорию;
- метку;
- комментарий;
- сумму;
- валюту;
- идентификатор группы;
- статус отмены.

Также желательно предусмотреть отдельный CSV-файл со сводкой по категориям.

Экспортированный файл пользователь сохраняет или передаёт через стандартное системное меню Android.

CSV не является основной базой данных и используется только для экспорта и резервного просмотра.

18. ПЕРЕНОС ДАННЫХ ИЗ СУЩЕСТВУЮЩЕЙ ТАБЛИЦЫ

Необходимо предусмотреть разовый перенос существующих данных.

Перед переносом пользователь предоставляет исходную таблицу в согласованном формате, предпочтительно XLSX или CSV.

Во время переноса:

- каждая колонка накоплений преобразуется в категорию;
- каждая заполненная денежная ячейка преобразуется в операцию;
- дата берётся из строки таблицы;
- значение дополнительного списка переносится как метка;
- положительные и отрицательные суммы сохраняют знак;
- пустые ячейки пропускаются;
- категории «Пусто 1», «Пусто 2», «Пусто 3» не переносятся, если в них нет операций.

После импорта необходимо сравнить:

- остаток каждой категории;
- общий остаток;
- количество операций;
- суммы пополнений;
- суммы списаний.

Импорт считается успешным, если рассчитанные приложением остатки совпадают с исходной таблицей.

19. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

Приложение должно:

- корректно работать без подключения к интернету;
- не терять локально сохранённые операции;
- не создавать дубликаты при повторной отправке;
- быстро открывать главный экран на основе локальной базы;
- корректно восстанавливаться после перезапуска;
- поддерживать небольшое потребление памяти сервера;
- учитывать ограниченные ресурсы VPS;
- не требовать постоянного запуска тяжёлых сервисов.

Сервер имеет ограниченные ресурсы:

- 1 vCPU;
- около 961 MiB RAM;
- около 58 ГБ диска;
- AmneziaVPN уже использует часть ресурсов.

Приложение Reserve_Sin не должно мешать работе AmneziaVPN.

20. БЕЗОПАСНОСТЬ

Обязательные требования:

- только HTTPS;
- Bearer-токен для всех методов /api/v1;
- API доступен через Caddy;
- Go API слушает только localhost;
- токен не попадает в логи;
- токен не хранится в Git;
- env-файл имеет ограниченные права;
- SQL-запросы выполняются с параметрами;
- входные данные проверяются;
- устанавливаются ограничения на размер HTTP-запроса;
- сервер не возвращает внутренние пути и stack trace;
- резервные копии имеют ограниченные права доступа.

23. КРИТЕРИИ ПРИЁМКИ

Проект считается выполненным, если:

1. Пользователь может добавить категорию через настройки.
2. Новая категория появляется на главном экране.
3. Категории «Пусто 1», «Пусто 2», «Пусто 3» изначально отсутствуют.
4. Пользователь может изменить порядок категорий.
5. Пользователь может архивировать и восстановить категорию.
6. Пользователь может создать пополнение.
7. Пользователь может создать списание.
8. Пользователь может добавить несколько категорий в одну групповую операцию.
9. Остаток категории рассчитывается правильно.
10. Общая сумма рассчитывается правильно.
11. После перезапуска приложения данные сохраняются.
12. Без интернета операция сохраняется локально.
13. После восстановления интернета операция отправляется на сервер.
14. Повторная отправка не создаёт дубликат.
15. История отображается по датам.
16. Историю можно фильтровать по категории и метке.
17. Операцию можно отменить без физического удаления.
18. Отменённая операция перестаёт влиять на остаток.
19. API недоступен без правильного Bearer-токена.
20. API работает только через HTTPS.
21. Сервер автоматически запускается после перезагрузки.
22. Ежедневная резервная копия создаётся автоматически.
23. Данные можно экспортировать в CSV.
24. После переноса существующей таблицы остатки совпадают с исходными значениями.
25. Работа Reserve_Sin не нарушает работу AmneziaVPN.

26. ИТОГОВЫЙ СТЕК

Android:

Kotlin + Jetpack Compose + Material 3 + MVVM + ViewModel + StateFlow + Room + Ktor Client + kotlinx.serialization + WorkManager + DataStore + Android Keystore.

Сервер:

Go + Chi + REST API + JSON + database/sql + SQLite + SQL-миграции + systemd + journald.

HTTPS:

Caddy + reserve-sin.duckdns.org.

Авторизация:

Один постоянный Bearer API-токен.

Синхронизация:

Local-first, Room, очередь операций, WorkManager, client_operation_id и серверная revision.

AmneziaVPN:

Отдельный независимый сервис. Не используется приложением Reserve_Sin и не изменяется в рамках проекта.
