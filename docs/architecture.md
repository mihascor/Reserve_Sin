# Архитектура

## Статус

Текущая версия `1.0.0` начинает этап закрытого веб-интерфейса после завершённого Android MVP `0.4.4`: Android local-first приложение использует Room для категорий, меток и операций, а Compose-экраны получают данные только через `ViewModel` и `Repository`. Пользователь может локально создавать, изменять и архивировать категории, а также создавать одиночные и групповые операции. Новые операции получают статус `PENDING`; отмена серверной операции сразу исключает её из локальных расчётов и получает `CANCEL_PENDING`, пока не будет отправлена на сервер. История читает локальные операции через Room, группирует строки с общим `batch_id` и показывает фильтры и подробности без обращения UI к API. Настройки сохраняют HTTPS-адрес через DataStore, а API-токен — в зашифрованном виде с ключом Android Keystore; Ktor-клиент синхронизирует данные по revision вручную и через WorkManager. Go-сервер содержит SQLite-миграции, Bearer-защиту `/api/v1`, операции, revision и `GET /health`.

```text
Android-приложение
  UI → ViewModel → Repository → Local Data Source (Room)
                              └→ Remote Data Source (Ktor Client)
                                             │ HTTPS + Bearer token
                                             ▼
                                         Caddy
                                             ▼
                                Go REST API (127.0.0.1:8080)
                                             ▼
                                          SQLite
```

Android-приложение должно быть local-first: Room хранит все данные, нужные интерфейсу; UI показывает локальное состояние и не обращается к базе или API напрямую. Каждому экрану назначается единый источник состояния через `ViewModel` и `StateFlow`.

`Repository` предоставляет главному экрану локальные сводные данные из Room, а экрану категории — её остаток и отфильтрованную историю. Экспорт получает полную историю из Room и записывает UTF-8 CSV через системный выбранный URI. Ручная и фоновая синхронизация отправляют новые категории без серверного ID, а изменённые серверные категории — через `PATCH`; их локальный статус синхронизации хранится в Room. Перед отправкой новых операций она передаёт отмены со статусом `CANCEL_PENDING`; после ответа сервера либо после `/changes` операция получает `SYNCED`. Затем она отправляет операции со статусом `PENDING` или `ERROR`; серверные ID и revision сохраняются в Room после успешного ответа. После отправки она получает `/changes` от сохранённой revision и применяет категории, метки и операции сервера в Room. При каждом старте `MainActivity` планирует уникальную немедленную задачу и периодическую задачу WorkManager с интервалом не менее 15 минут; обе требуют сети, а неудачный запрос повторяется с экспоненциальной задержкой. Без сохранённого токена worker не выполняет сетевой запрос. При создании операции Android сохраняет уникальный `client_operation_id` и статус синхронизации.

Go API принимает HTTPS-запросы только через Caddy. Сам API должен слушать `127.0.0.1:8080`; SQLite является серверным хранилищем истории, категорий и меток. Подробнее о данных — в [документации базы данных](database.md), об API — в [документации API](api.md).

## Закрытый веб-интерфейс

Веб-интерфейс обслуживается Caddy как статические HTML, CSS и Vanilla JavaScript-файлы из `web/app/`. Страница `/app/` предназначена только для чтения истории и обращается к Go API через тот же origin по `/app-api/api/v1/web-history`. Caddy защищает оба маршрута Basic Auth и сам добавляет Bearer-токен при проксировании на `127.0.0.1:8080`; браузер токен не получает. Существующий `/api/v1/*` остаётся маршрутом Android с самостоятельной Bearer-проверкой.

Для страницы истории Go API предоставляет отдельный read-only маршрут `GET /api/v1/web-history` с выдачей неотменённых операций активных категорий. Это не меняет контракт текущего `/api/v1/transactions`. Решение зафиксировано в [ADR 003](decisions/003-web-history-interface.md).

Сервер использует стандартный `log/slog` как общий механизм журналирования. Middleware создаёт `request_id`, добавляет его в контекст запроса и записывает безопасные сведения о завершении HTTP-запроса. Текстовый формат предназначен для разработки, JSON — для production; подробности — в [конфигурации](configuration.md#логирование-сервера).

## Неопределённое

ТЗ не задаёт состав модулей, классов, DTO, формат успешных ответов и стратегию разрешения конфликтов одновременных локальных и серверных изменений. Сопоставление ID категорий теперь определено: Android отправляет стабильный локальный ID как `client_category_id`, сервер хранит его уникально и возвращает вместе с категорией. Остальные детали нельзя считать принятыми до реализации.
