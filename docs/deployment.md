# Развертывание и резервное копирование

## Статус

На VPS с Ubuntu 24.04.4 LTS подтверждено работающее production-развёртывание: `reserve-sin.service` и `reserve-sin-backup.timer` включены и активны, API отвечает на локальный `GET /health`, а Caddy слушает публичные порты 80 и 443. Go API слушает только `127.0.0.1:8080`; на момент проверки создана SQLite-резервная копия и systemd зафиксировал её успешное создание.

Сквозная проверка Android ↔ production-сервер и проверка процедуры восстановления резервной копии ещё не подтверждены. Они должны выполняться только с тестовыми данными до переноса фактической истории.

## Следующий этап

Следующий инфраструктурный этап — сквозная проверка уже развернутого контура синхронизации на реальном сервере с тестовыми данными. Она включает Android-подключение по HTTPS/Bearer, отправку и получение данных, проверку идемпотентности и документированную проверку восстановления SQLite-копии.

Следующая инфраструктурная проверка — с Android-устройства подтвердить подключение по Bearer-токену, ручную синхронизацию категорий и одиночных/групповых операций, получение изменений с сервера, идемпотентный повтор отправки и сохранность данных после перезапуска сервера. До завершения отмены операций и подтверждения резервного восстановления для этой проверки используются только тестовые данные; перенос фактической истории откладывается.

После сквозной проверки следующим функциональным этапом остаются отмена операций и синхронизация её статуса на Android.

## Материалы установки

| Файл | Назначение |
| --- | --- |
| `deploy/systemd/reserve-sin.service` | Запуск API от системного пользователя `reserve-sin`. |
| `deploy/systemd/reserve-sin-backup.service` | Однократный запуск резервного копирования. |
| `deploy/systemd/reserve-sin-backup.timer` | Ежедневный запуск резервного копирования в 03:15 UTC с выполнением пропущенного запуска после включения сервера. |
| `deploy/caddy/Caddyfile` | Публикация домена через Caddy и proxy на локальный API. |
| `deploy/scripts/backup-reserve-sin.sh` | Резервное копирование через SQLite backup API, проверка целостности и хранение 14 последних суток. |

## Установка на VPS

Команды ниже выполняются администратором Ubuntu 24 после передачи на сервер собранного бинарника и файлов из `deploy/`. Они не меняют настройки AmneziaVPN.

1. Установить пакет `sqlite3`, создать системного пользователя без входа и каталоги: `/opt/reserve-sin`, `/etc/reserve-sin`, `/var/lib/reserve-sin`, `/var/backups/reserve-sin`. Каталоги с бинарником, базой и копиями должны принадлежать `reserve-sin`; каталог `/etc/reserve-sin` остаётся под управлением администратора.
2. Поместить бинарник в `/opt/reserve-sin/reserve-server`, скрипт в `/opt/reserve-sin/backup-reserve-sin.sh`, назначить владельцем файлов пользователя `reserve-sin`. Бинарник и скрипт должны быть исполняемыми.
3. На основе [примера параметров](../server/reserve.env.example) создать `/etc/reserve-sin/reserve.env`, задать случайный `RESERVE_SIN_API_TOKEN` и ограничить доступ к файлу владельцем `root` и режимом `0600`.
4. Установить systemd-файлы в `/etc/systemd/system/`, затем выполнить `systemctl daemon-reload`, включить и запустить `reserve-sin.service` и `reserve-sin-backup.timer`.
5. Подключить `deploy/caddy/Caddyfile` к действующей конфигурации Caddy и проверить её штатной командой проверки конфигурации Caddy перед reload. Caddy должен быть единственным публичным входом; Go-сервер остаётся на `127.0.0.1:8080`.
6. Проверить `GET /health` локально на VPS и затем по HTTPS снаружи. После этого создать на Android только тестовые категории и операции, вручную синхронизировать их и повторить отправку тех же данных.

Точный способ передачи файлов, установка Caddy и DNS зависят от текущей конфигурации VPS и перед выполнением должны быть сверены с ней. Настоящий токен не передаётся через Git, документацию или командную историю.

## Целевое размещение

Сервер должен работать на Ubuntu 24 без Docker для Reserve_Sin. Go-сервис запускается от отдельного системного пользователя `reserve-sin` через systemd, с автоматическим запуском после перезагрузки и перезапуском после ошибки. Логи ведутся в journald и не должны содержать API-токен или полные тела конфиденциальных запросов.

Для production в `/etc/reserve-sin/reserve.env` нужно задать `RESERVE_SIN_ENV=production` и выбрать `RESERVE_SIN_LOG_LEVEL`. `slog` записывает JSON в stdout, а systemd/journald собирает его как стандартный вывод процесса. Смотреть записи следует через `journalctl -u reserve-sin`; отдельное внешнее хранилище логов не используется и его отказ не влияет на работу приложения.

| Ресурс | Целевое расположение |
| --- | --- |
| Бинарник | `/opt/reserve-sin/reserve-server` |
| SQLite | `/var/lib/reserve-sin/reserve.db` |
| Конфигурация и токен | `/etc/reserve-sin/reserve.env` |
| Резервные копии | `/var/backups/reserve-sin/` |

Go API слушает только `127.0.0.1:8080`. Caddy публикует `https://reserve-sin.duckdns.org` и проксирует запросы к нему. Снаружи нужны только порты `80` и `443`; существующие порты AmneziaVPN не изменяются. Права должны ограничивать доступ посторонних пользователей к env-файлу, базе и резервным копиям.

## Резервное копирование и восстановление

ТЗ требует ежедневную автоматическую копию SQLite, хранение нескольких последних копий, удаление старых по сроку (рекомендовано 14 дней), журналирование результата и ручной запуск. Для активной базы в WAL запрещён обычный `cp`; допустимы SQLite backup API или `VACUUM INTO`.

Скрипт `deploy/scripts/backup-reserve-sin.sh` использует команду SQLite `.backup`, то есть SQLite backup API; активная база в WAL не копируется через `cp`. До публикации итоговой копии выполняется `PRAGMA integrity_check`; неуспешная временная копия удаляется. Таймер запускает скрипт ежедневно, а файлы старше 14 суток удаляются после успешного создания новой копии. Для ручного запуска используется `systemctl start reserve-sin-backup.service`.

Для восстановления нужно остановить `reserve-sin.service`, сохранить текущую базу отдельно, проверить выбранную резервную копию через `sqlite3 /путь/к/копии 'PRAGMA integrity_check;'`, заменить файл базы этой копией с владельцем `reserve-sin` и режимом `0600`, затем запустить сервис и проверить `/health`. Эту процедуру необходимо один раз проверить на тестовых данных на VPS до переноса фактической истории.
